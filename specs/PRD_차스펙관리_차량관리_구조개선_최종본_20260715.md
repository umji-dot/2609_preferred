## 1. 개요 (Overview)

### 1.1 상위 프로젝트 연계

본 프로젝트는 **차량정보 통합DB 구축** (`차량정보_통합_시스템/01_진행중_프로젝트/차량정보_통합DB_구축`)의 하위 선결 과제입니다.

상위 프로젝트(통합DB 구축)의 FMS 차량등록 화면 개선(`PRD_차량등록_화면_개선.md v2.0`)에서는 차량 등록 시 **차량등록증 업로드(Path A)** 또는 **차량번호 직접 조회(Path B)** 방식을 도입하고, VIN 기반 통합DB 연동, 소유주 검증 API 연동 등을 계획하고 있습니다.

이를 실현하기 위해서는 FMS 어드민 내 **차량 등록 진입점**이 현재 `카코드 관리` 메뉴에 종속되어 있는 구조를 먼저 해소해야 합니다. 또한, 향후 통합DB에서 차량 식별 기준으로 사용할 VIN, 차명 등의 통합DB 필드는 이번 개선 후 차량 등록 모달에 추가될 예정이나, 해당 필드 추가는 **통합DB 구축 프로젝트에서 별도 진행**합니다.

### 1.2 이번 프로젝트 목표

1. **카코드 관리**: 역할을 카코드 관리 전용으로 명확히 분리
2. **차량관리**: 차량 등록·수정·삭제의 단일 진입점으로 통합
3. 양 메뉴 간 불필요한 종속성 제거 및 독립적 운용 가능 구조 확보
4. UX 정리: 불필요한 필터, 컬럼, 하위 탭 제거 및 용어 통일

### 1.3 이번 프로젝트 범위 (In Scope)

- FMS 어드민 > 차량관리 LNB 하위 메뉴 구조 개편
- 카코드 관리 화면: 기능 분리, 불필요 UI 요소 정리, 용어 통일
- 차량관리 화면: 차량 등록/일괄등록 기능 이전, 불필요 UI 요소 정리
- **차량 수정(상세보기) 팝업 필드 변경**: 통합DB 연동을 위한 신규 필드(VIN, 인증 상태 등) 추가 및 기존 필드 재구성
- **차량 등록 모달 UX 개선 (Path A/B/C 구조 적용)**: `PRD_차량등록_화면_개선.md v2.0 §3` 기준. 차량등록증 업로드(Path A), 차량번호 조회(Path B), 직접 입력(Path C) 3경로 UI 구현. VIN, 인증 상태 뱃지, 자동 채움 필드 포함
- 카코드 용어 통일 (UI 레이블 기준)

### 1.4 이번 프로젝트 범위 외 (Out of Scope)

- 통합 Vehicle API 백엔드 설계 및 DB 스키마 → **통합DB 구축 프로젝트** (MVP: 각 서비스로부터 들어오는 차량 데이터를 통합DB에 저장하는 백엔드/API)
- OCR 서비스, 소유주 검증 API 서버 구현 → **통합DB 구축 프로젝트**
- 차량 등록 Path A/B/C에 사용되는 **OCR 서버, 소유주 검증 API 서버 구현** → **통합DB 구축 프로젝트** (UI는 본 프로젝트 범위이나, API 백엔드는 통합DB 구축 프로젝트에서 담당)
- 카코드 통합/폐합 기능 → 본 PRD §8 차선 과제 섹션 정의, 우선순위 별도 논의
- 기존 5만 대 차량 데이터 VIN 마이그레이션 → **통합DB 구축 프로젝트**
- 통합DB N-01 전파 알림 수신 후 FMS 데이터 자동 동기화 로직 → **통합DB 구축 프로젝트** 완료 후 별도 진행

> ℹ️ **역할 분리 원칙**: 통합DB 구축 프로젝트는 DB/API MVP(각 서비스→통합DB 데이터 저장)를 담당합니다. FMS 어드민 화면의 모든 UI 변경(등록 모달, 수정 팝업 등)은 본 프로젝트(차스펙관리_차량관리_구조개선)에서 진행합니다.

### 1.5 대상 플랫폼 및 사용자

## 2. 현행 구조 분석 (As-Is)

### 2.1 메뉴 구조 (현행)

```
차량관리 (LNB)
├── 카코드 관리               ← 차량 등록의 유일한 진입점 (구조적 문제)
│   ├── [탭] 카코드 관리      ← 카코드 목록 + 차량등록 버튼 공존
│   └── [탭] 차모델코드 관리  ← 카코드 관리와 기능 중복 (불필요)
└── 차량 관리               ← 수정/삭제만 가능, 등록 불가
```

| # | 문제 | 설명 | 영향 |
| :--- | :--- | :--- | :--- |

| P-02 | 등록 진입점 불일치 | 차량 등록이 카코드 관리 메뉴에 위치 | 메뉴 목적과 기능 불일치, 운영자 혼란 |

#### 4.1.2 카코드 등록/수정 화면 필드 명세

> **등록하기 버튼 역할 (Path A)**: 폼 제출 → 등록증 S3 영구 저장 (`vehicle_registration_docs` INSERT) → 소유주 검증 API 백그라운드 호출 (약 3~5초) → VERIFIED 완료 → `vehicle_immutable` INSERT + `vehicle_mutable` INSERT (통합DB PRD §6.1) → FMS 자체 DB에 `fms_vehicle.master_id = vehicle_immutable.id` 업데이트.

> ℹ️ **등록하기 클릭 시 검증 순서 (260715 갱신)**: [등록하기] 버튼 클릭 시 **① FMS 자체 차대번호·차량번호 중복 체크(Path A/B/C 공통, [기능 B-2-5], BR-34)**를 최우선으로 수행하고, 중복이 없을 때에만 ② 기존 등록 플로우를 진행한다. **Path A(차량등록증 업로드)에서만** OCR 완료 후 VIN 17자리가 확정되면 추가로 통합DB에 VIN 기준 중복 조회를 수행한다. Path B/C는 통합DB를 조회하지 않고 항상 임시DB(`vehicle_temp`)에 등록한다. **Case A**: 신규 차량이면 정상 진행. **Case B (동일 등록증 중복)**: 동일 VIN + 동일 발부일자 등록증이 이미 존재하면 "이미 등록된 차량 등록증입니다" 안내만 표시하고 추가 차량 등록을 차단한다. **Case C (동일 VIN, 다른 등록증)**: 동일 VIN이지만 발부일자가 다른 등록증이 이미 존재하는 경우로, **Case C-1**(업로드본이 최신 또는 동일)은 "해당 차량의 이전 등록증 이력이 존재합니다" 안내만 표시하고 정상 진행하며, **Case C-2**(업로드본이 기존 최신 등록증보다 구버전, 260715 신규)는 자동 채움 값을 기존 최신 등록증 데이터로 대체하고 "업로드된 등록증보다 더 최신화된 등록증이 있습니다. 차량등록증을 다시 확인하세요." 안내 팝업을 표시한다(등록 차단 아님). 백엔드에서 vehicle_registration_docs 이력으로 관리. **FMS 서비스 연결 버튼은 제공하지 않는다.** [기능 B-2-4], [기능 B-2-5], BR-23, BR-34, BR-35 참조.

> ℹ️ **자동 채움 필드 수정 가능 원칙**: OCR/API로 자동 채워진 모든 필드는 [등록하기] 버튼 클릭 전까지 운영자가 직접 수정 가능하다. 자동 채움 후 수정된 필드는 파란 배경을 유지한다. BR-26 참조.

> ℹ️ **서버 반영 카코드 필터 조건 (변경-AA)**: 서버 반영 카코드 드롭다운에는 기등록된 카코드 중 차량 정보에 입력된 데이터(제조사·모델명·연식)가 동일한 카코드만 표시한다. 드롭다운 각 항목에는 카코드명 + 카코드 정보에 등록된 연식·하위모델명·유종·배기량·길이를 함께 표시한다.

> ℹ️ **종합검사 주기 자동 계산 (변경-AA)**: 사업용 승용차이므로 최초 등록일 기준 2년 이후 매년으로 자동 입력된다. 다음 종합검사 만기일은 차량 등록증 내 정보를 기반으로 자동 계산되며, 운영자가 수정 가능하다.

> ℹ️ **자동 채움 시각 처리**: OCR/API 자동 채움 필드 = 연한 파란색 배경 + 좌측 파란 세로선. OCR 신뢰도 낮은 필드(< 80%) = 주황색 배경 + ⚠ 아이콘. 수동 입력 필수 필드(Path B/C) = 빨간 테두리. ~~Path A API 전용 필드 = 회색 플레이스홀더 "등록 완료 시 자동 채움" (readonly)~~ **폐기 (260715)** — 해당 방식이 적용되던 제조사·모델명 필드가 전 Path 공통 imsform DB 캐스케이드 드롭다운으로 전환되어 더 이상 사용하지 않음.

> ℹ️ **카코드 매칭 자동 채움 (BR-21, 변경-AA)**: 서버 반영 카코드 드롭다운에서 카코드를 선택하면, 해당 카코드에 저장된 차량 제원 정보(유종·배기량·길이 등)가 차량 정보 필드에 자동으로 채워집니다. 단, Path A(OCR 자동 채움) 또는 Path B(API 자동 채움) 상태에서 이미 자동 입력된 필드는 덮어쓰지 않고 "카코드 정보와 다를 수 있습니다. 직접 확인해 주세요." 확인 toast를 표시합니다.

#### 4.2.3 차량 일괄등록 — 등록 예정 목록(Staging) in-modal 방식 (v1.4 재설계)

**차량 등록 팝업(§4.2.2) 내부**에서 다건 차량을 처리합니다. 각 경로(Path A/B/C)에서 데이터가 확정되면 팝업 하단 **등록 예정 목록**에 자동 또는 명시적으로 누적되고, 목록이 쌓이면 [등록하기 (N건)] 버튼으로 일괄 등록합니다. 별도 팝업(modal-bulk-staging)은 사용하지 않습니다.

  [N (취소)]          → 컨펌창 닫기

매각 상태로 전환된 차대번호는 신규 차량 등록 가능.
```

```

**삭제 버튼 정책 (BR-31, 260609)**

삭제 버튼은 팝업 내부에 위치하며, 서비스 DB에서만 삭제됩니다 (차량 DB 유지).

| 조건 | 삭제 가능 여부 | 비고 |
| :--- | :--- | :--- |
| 단말기 연결 **있음** | 불가 (버튼 비활성화) | — |
| 단말기 연결 **없음** | 가능 | 서비스 DB에서만 삭제. 차량 DB(통합DB)에서는 삭제되지 않음 |

> ℹ️ **VIN·연식 읽기전용 근거 (BR-25)**:
> - **차대번호(VIN)**: 차량의 법적 고유 식별자(ISO 3779 표준). Case 2(등록증 있음): 등록증 기반으로 확정된 값이므로 읽기 전용. 임의 변경 시 통합DB 정합성이 깨지므로 SYS_ADMIN 권한으로만 변경 가능. Case 1(등록증 없음): 운영팀이 수동 입력/수정 가능.
> - **연식(제조년도)**: 데이터 출처는 **VIN 10번째 자리(ISO 3779, Model Year 인코딩)**. 차량 등록증의 최초등록일(등록일)을 기준으로 연식을 산출하지 않는다. Case 2(등록증 있음): VIN 기반으로 확정된 값이므로 읽기 전용. SYS_ADMIN 권한으로만 변경 가능. Case 1(등록증 없음): 운영팀이 VIN 기준으로 수동 수정 가능.

> ℹ️ **초기 배포 시 VIN 데이터**: 통합DB 구축 프로젝트 MVP 완료 이전에는 VIN 필드가 비어 있을 수 있습니다. 이 경우 VIN 필드는 "미등록" 상태로 표시하고, 인증 상태는 "미인증(UNVERIFIED)"으로 표시합니다.

## 6. BDD — 행위 기반 상호작용 명세

### [기능 A-1] 카코드 관리에서 카코드 독립 관리

- **Given**: 운영자가 FMS 어드민 > 차량관리 > 카코드 관리에 진입한 상태에서
- **When**: 화면을 로드하면
- **Then**:
  - 상단에 '카코드 관리' 단일 탭만 표시된다. '차모델코드 관리' 탭은 표시되지 않는다.
  - 필터 영역에 제조사, 모델명, 연식, 카코드 검색 필드만 표시된다. 연료종류, 배기량, 기타포함 체크박스는 표시되지 않는다.
  - 상단 버튼으로 [조회], [엑셀 다운로드], [카코드 등록]만 표시된다. [카코드 일괄등록] 버튼과 [차량 일괄등록] 버튼은 표시되지 않는다. [엑셀 다운로드] 클릭 시 목록 테이블 데이터와 카코드 수정 팝업(상세화면) 데이터를 함께 포함한 xlsx가 다운로드된다. (260715)
  - 테이블에 차량등록 버튼 컬럼이 표시되지 않는다.
  - 테이블 컬럼에 연비 컬럼이 표시되지 않는다. 길이 컬럼은 표시된다 (260615 복원, 변경-R).
  - 테이블 컬럼에 ID, 차량이미지, 상세보기 버튼 컬럼이 표시되지 않는다. 차량이미지는 차량관리 테이블로 이동하였다. (260715)
  - 테이블의 첫 번째 컬럼은 **카코드**이며, 링크 형태로 표시되어 클릭 시 카코드 수정 팝업이 열린다. (260715)
  - 테이블의 '리버스여부' 컬럼명이 '리버스'로 표시된다.
  - 테이블의 컬럼명이 '하위모델명'으로 표시된다. (260609: 보조모델명 → 하위모델명 복귀)
  - 테이블의 '모델코드' 컬럼이 '카코드'로 표시된다.

### [기능 A-2] 카코드 등록

- **Given**: 운영자가 카코드 관리 화면에서 [카코드 등록] 버튼을 클릭한 상태에서
- **When**: 카코드 등록 화면이 표시되면
- **Then**:
  - 차량이미지(선택), 국산/수입 구분(필수), 제조사(필수), 모델명(필수), 카코드 파일(fbp)(선택), 카코드(필수), 버전(선택), 연식-YYYY(필수), 유종(필수) 필드가 노출된다. (260609)
  - **하위모델명(필수), 단종연도(필수), 길이(필수), 배기량(필수) 필드가 필수 입력으로 노출된다.** (변경-S)
  - 승차인원, 퓨즈유형, 리버스, 차량종류, 연비 필드는 표시되지 않는다 (제거).
  - [취소], [등록] 버튼이 표시된다.
  - 필수 필드 미입력 시 '필수 입력 값입니다' 에러 메시지가 해당 필드 하단에 표시된다.
  - 등록 성공 시 카코드 목록 화면으로 돌아가고, 새로 등록된 카코드가 목록에 표시된다.

### [기능 A-2-1] 카코드 등록 — 제조사·모델명 연동 선택

- **Given**: 운영자가 [카코드 등록] 버튼을 클릭하여 카코드 등록 화면이 열린 상태에서
- **When**: 국산차/수입차 라디오 버튼을 선택하면
- **Then**:
  - 제조사 드롭다운에 선택한 구분(국산차/수입차)에 해당하는 브랜드 목록만 표시된다.
  - 국산차 선택 시: 현대, 기아, 제네시스, 르노삼성, 쉐보레, 쌍용, 예스알브이, 스타모빌, 다온티앤티, 기타_국산 목록이 표시된다.
  - 수입차 선택 시: 벤츠, BMW, 아우디 등 55개 수입 브랜드 목록이 표시된다.
  - 모델명 드롭다운은 비활성화 상태(회색)로 표시된다.

- **When**: 제조사 드롭다운에서 특정 브랜드를 선택하면
- **Then**:
  - 모델명 드롭다운이 활성화되고, 선택한 브랜드에 속하는 모델 목록이 표시된다.
  - 예시: 제조사 = '현대' 선택 시 → i30, i40, 그랜저, 넥쏘, 마이티, 맥스크루즈, 베뉴, 베라크루즈, 벨로스터, 스타렉스, 스타리아, 싼타페, 쏘나타, 쏠라티, 아반떼, 아슬란, 아이오닉, 아이오닉 5, 아이오닉 6, 에쿠스, 엑센트, 카운티, 캐스퍼, 코나, 투싼, 팰리세이드, 포터 표시.

### [기능 A-2-2] 카코드 수정 — 기존 값 pre-select

- **Given**: 운영자가 카코드 관리 목록 테이블에서 기존 카코드의 **카코드(링크)를 클릭**한 상태에서 (260715: 상세보기 버튼 → 카코드 링크로 대체)
- **When**: 카코드 수정 화면이 열리면
- **Then**:
  - 기존 저장된 제조사 값에 해당하는 국산/수입 구분이 자동으로 선택된다.
  - 기존 저장된 제조사 값이 드롭다운에서 선택 상태로 표시된다.
  - 기존 저장된 모델명 값이 드롭다운에서 선택 상태로 표시된다.
  - 기존 저장된 제조사/모델명이 imsform DB에 없는 경우(레거시 데이터): 해당 필드에 기존 텍스트 값이 유지되며, 운영자가 DB 기반 값으로 재선택하거나 그대로 유지할 수 있다.
  - **카코드 입력창은 비활성화(disabled) 상태로 표시되어 수정할 수 없다.** (260715 신규)
  - 읽기 전용으로 분류된 다른 필드가 있는 경우 동일하게 입력창이 비활성화 상태로 표시된다. (260715 신규)

### [기능 B-1] 차량관리에서 차량 등록

- **Given**: 운영자가 FMS 어드민 > 차량관리 > 차량 관리에 진입한 상태에서
- **When**: 화면을 로드하면
- **Then**:
  - 상단 버튼으로 [엑셀 다운로드], **[차량 등록]** 버튼이 표시된다. [현장 서비스 신청] 버튼, [차량 일괄등록] 버튼은 표시되지 않는다. [엑셀 다운로드] 클릭 시 목록 테이블 데이터와 차량 수정(상세보기) 팝업 데이터를 함께 포함한 xlsx가 다운로드된다. (260715)
  - 필터 영역에 리셀러, 업체, 지점, 단말기 장착여부, 차량상태, 카코드 선택 여부, 차량등록증 등록 여부, 검색 필드가 표시된다. 현장서비스 진행여부 필터는 표시되지 않는다.
  - 테이블 컬럼 순서: ID → **차량이미지** → 리셀러 → 업체명 → 지점명 → **차대번호(링크)** → 차량번호 → 연식 → 제조사 → 모델명 → 하위모델명 → 단말기 기종 → 단말기 SN → **연료종류** → 주행거리 → 통신모드 → 최초 설치일 → 최근 설치일 → 탈거일 → 카코드 → **차량등록증 등록 여부** → 차량상태. (변경-T/U/V/W, 260715 전면 재편)
  - 테이블의 'nonOBD 여부' 컬럼명이 '통신모드'로 표시된다.
  - 테이블에 **단말기 기종** 컬럼이 표시된다. (변경-U)
  - 테이블 컬럼명이 '단말기 일련번호'가 아닌 **'단말기 SN'** 으로 표시된다. (변경-W)
  - 테이블에 **차량이미지** 컬럼이 표시된다. 카코드 관리 테이블에서 이관됨 (260715)
  - **차대번호** 컬럼이 링크 형태로 표시되며, 클릭 시 상세보기(수정) 팝업이 열린다. (260715)
  - 테이블 컬럼명이 '유종'이 아닌 **'연료종류'**로 표시된다. (260715, 차량관리 한정)
  - 테이블 컬럼명이 '차량등록증 여부'가 아닌 **'차량등록증 등록 여부'**로 표시된다. (260715)
  - 테이블에 디지털 차키 여부, 상세보기 버튼 컬럼은 표시되지 않는다. (260715)
  - 현장서비스 진행여부, 현장서비스 신청일 컬럼은 표시되지 않는다.

### [기능 B-2] 차량 등록 — 등록 경로 선택

  - Path A(OCR 자동 채움) 또는 Path B(API 자동 채움) 상태에서 이미 자동 입력된 필드는 덮어쓰지 않고 "카코드 정보와 다를 수 있습니다. 직접 확인해 주세요." toast를 표시한다. (BR-21)

### [기능 B-2-1] 차량 등록 — Path A (차량등록증 업로드)

  - "① 파일 검증 중..." 상태 표시
  - 등록증 사전 검증 요청 (파일이 차량등록증인지 확인) → "② 등록증 확인 중..." 표시 (BR-24)

  - 사전 검증 성공 시: "③ 등록증 분석 중... (약 15~30초 소요)" 표시 (비동기 OCR 처리 중)
  - OCR 완료 후 (Webhook 수신): VIN·차량번호·하위모델명(가능 시)·연식·최초등록일·유종·배기량(가능 시)·길이(가능 시) → 파란 배경으로 자동 채움. (변경-X: 차명 필드 제거, 하위모델명 선택 채움으로 변경)

  - **제조사·모델명 필드**: imsform DB 캐스케이드 드롭다운(국산/수입 → 브랜드 → 모델)으로 표시된다. OCR이 브랜드·모델 정보를 추출한 경우 해당 값으로 사전 선택되며, 추출하지 못한 경우 미선택 상태로 표시되어 운영자가 직접 선택한다. 선택 후에도 [등록하기] 클릭 전까지 자유롭게 변경 가능하다. (260715 변경 — 기존 "등록 완료 시 자동 채움" readonly 표시 방식 폐기)
  - VIN 자동 채움 즉시: 통합DB에 VIN 기준 중복 조회 수행. 기존 차량 확인 시 안내 배너 표시. [기능 B-2-4], BR-23 참조.
  - 안내 메시지: "OCR 분석 완료 · 내용을 확인하고 등록하기를 눌러 주세요."
- **When**: 운영자가 [등록하기] 버튼을 클릭하면
- **Then (Frontend — 등록 단계)**:
  - 버튼 로딩 상태: "등록 중... (소유주 검증)"으로 전환 (중복 클릭 방지)
  - 약 3~5초 후 완료
  - 성공 시: VERIFIED 뱃지 + "등록이 완료되었습니다. VERIFIED 상태로 저장되었습니다." 메시지
  - API 실패 시: VERIFIED 뱃지 + "등록이 완료되었습니다. 제조사·모델 정보는 운영팀이 보완 예정입니다." 메시지
- **Then (Backend/API)**:
  - 등록증 S3 영구 저장
  - `vehicle_registration_docs` INSERT (is_verified_source = true, source_service = 'FMS')
  - 소유주 검증 API 자동 호출 (차량번호 + OCR 소유자명). 비동기 Webhook 방식으로 처리.
  - 실패 시 Upstage fallback 소유자명으로 재시도. 모두 실패 시 OCR 데이터만으로 VERIFIED 저장 + Slack 알림
  - `vehicle_immutable INSERT` + `vehicle_mutable INSERT` (통합DB PRD §6.1, verification_status = VERIFIED, data_source = 'OCR', source_service = 'FMS')
  - FMS 자체 DB: `fms_vehicle.master_id = vehicle_immutable.id` 업데이트 (통합DB는 서비스 연결 정보 저장하지 않음)

  - VIN 기반 차량 조회 API 호출 → 응답 데이터 폼 자동 채움

  - FMS 자체 DB: `fms_vehicle.temp_vehicle_id = vehicle_temp.id` 기록 (통합DB는 서비스 연결 정보 저장하지 않음)

### [기능 B-2-4] 차량 등록 — Path A VIN 기반 통합DB 중복 체크 (BR-23)

> **배경**: Path A(차량등록증 업로드)에서 OCR 완료 후 VIN이 확정된 경우, 통합DB에 중복 조회를 수행하여 케이스별로 처리한다. Path B/C는 통합DB를 조회하지 않고 항상 임시DB에 등록한다. FMS 서비스 연결 버튼은 제공하지 않는다 (운영자 혼란 방지).

- **Given**: Path A에서 차량 등록 모달의 OCR 완료로 VIN 17자리가 확정된 상태에서
- **When**: 시스템이 통합DB에 VIN 기준 중복 조회를 수행하면

#### Case A — 신규 차량 (통합DB에 미존재)

- **Then (Frontend)**:
  - 안내 없이 정상적으로 등록 흐름을 계속 진행한다.
- **Then (Backend/API)**:
  - `GET /api/v1/vehicles?vin={vin}` → HTTP 404 → 신규 등록 흐름 계속.

#### Case B — 동일 등록증 중복 (동일 VIN + 동일 발부일자 등록증이 이미 존재)

- **Then (Frontend)**:
  - "이미 등록된 차량 등록증입니다. 동일한 등록증으로 차량이 기등록되어 있습니다." 안내 배너 표시.
  - 추가 차량 등록 차단. [등록하기] 버튼 비활성화.
- **Then (Backend/API)**:
  - `GET /api/v1/vehicles?vin={vin}` + `vehicle_registration_docs` 발부일자 비교 → 동일 발부일자 존재 확인.
  - 등록 요청 차단.

#### Case C — 동일 VIN, 다른 등록증 (VIN은 동일하지만 발부일자가 다른 등록증)

> **[260715 변경] Case C는 업로드된 등록증과 기존 최신 등록증의 발부일자를 비교하여 C-1/C-2로 분리한다.**

##### Case C-1 — 업로드된 등록증이 기존 최신 등록증보다 최신(또는 동일)인 경우

- **Then (Frontend)**:
  - "해당 차량의 이전 등록증 이력이 존재합니다." 안내 배너만 표시.
  - 차량 등록은 정상 진행 가능. [등록하기] 버튼 활성 유지.
- **Then (Backend/API)**:
  - 기존 차량과 동일한 `vehicle_id` 에 새 등록증 이력을 `vehicle_registration_docs`에 INSERT.
  - `vehicle_immutable`/`vehicle_mutable` 데이터는 신규(업로드된) 등록증 기준으로 업데이트 (발부일자 기준, 통합DB PRD §6.5 충돌 처리 플로우 준용).
  - HTTP 201 Created 반환.

##### Case C-2 — 업로드된 등록증이 기존 최신 등록증보다 이전(구버전)인 경우 (260715 신규, BR-35)

- **Then (Frontend)**:
  - 자동 채움 필드 값을 업로드된 등록증의 OCR 값이 아닌 **차량 DB에 존재하는 최신 등록증 데이터로 대체**하여 표시한다.
  - "업로드된 등록증보다 더 최신화된 등록증이 있습니다. 차량등록증을 다시 확인하세요." 안내 팝업을 표시한다.
  - 안내 팝업 확인 후 등록 자체는 차단하지 않는다. 운영자가 최신 데이터를 확인한 뒤 [등록하기]를 진행할 수 있다.
- **Then (Backend/API)**:
  - `vehicle_registration_docs` 발부일자 비교로 업로드본이 구버전임을 확인.
  - 폼 자동 채움 값을 최신 등록증(`vehicle_immutable`/`vehicle_mutable` 현재 값) 기준으로 재설정하여 응답.
  - 업로드된 구버전 등록증도 이력으로 `vehicle_registration_docs`에 INSERT (이력 보존 목적, `is_verified_source = false`).
  - HTTP 200 OK 반환 (자동 채움 값 갱신 응답). [기능 B-2-4 Case C-2], BR-35 참조.

### [기능 B-2-5] 차량 등록 — FMS 자체 차대번호·차량번호 중복 등록 방지 (260715 신규, BR-34)

> **배경**: 통합DB VIN 중복 체크([기능 B-2-4], BR-23)는 Path A 전용이며 통합DB 기준으로 판단한다. 이와 별개로, FMS 자체 차량관리 데이터 기준으로 **이미 등록되어 있고 매각 처리되지 않은(운영 중) 차량과 차대번호 또는 차량번호가 동일**한 경우를 차단하는 검증을 **Path A/B/C 공통**으로 추가한다.

- **Given**: 운영자가 차량 등록 모달(Path A/B/C 무관)에서 차대번호·차량번호를 포함한 등록 정보를 입력한 상태에서
- **When**: [등록하기] 버튼을 클릭하면
- **Then (Frontend)**:
  - 시스템이 **[기능 B-2-4]의 통합DB VIN 중복 체크(Path A 전용)보다 먼저** FMS 자체 차량관리 데이터를 대상으로 중복 여부를 확인한다.
  - 동일한 차대번호 또는 동일한 차량번호를 가진 **운영 중(차량상태 ≠ 매각) 차량이 이미 존재**하면 "동일한 차대번호(차량번호)가 존재합니다. 기존 차량을 매각 처리한 후 다시 등록하세요." 안내 팝업을 표시하고 등록을 차단한다. [등록하기] 버튼은 비활성화되지 않으나 제출은 차단되며 팝업 확인 후 입력 화면으로 복귀한다.
  - 매각 처리된(차량상태 = 매각) 동일 차대번호·차량번호 차량은 중복으로 간주하지 않고 정상 등록을 허용한다.
  - 중복이 없으면 정상적으로 다음 단계(Path A의 경우 [기능 B-2-4] 통합DB 중복 체크)를 진행한다.
- **Then (Backend/API)**:
  - 차대번호·차량번호 기준 FMS 자체 DB(운영 중 차량 한정) 조회 API 호출 (API 상세는 FMS 서버팀 협의 필요, TBD-11).
  - 중복 확인 시 등록 요청을 차단하고 사유를 반환한다.
  - 중복이 없으면 등록 흐름을 계속 진행한다.

### [기능 B-4] 차량 수정 — 개선된 팝업

- **Given**: 운영자가 차량관리 테이블에서 특정 차량의 **차대번호(링크)를 클릭**한 상태에서 (260715: 상세보기 버튼 → 차대번호 링크로 대체)
- **When**: 상세보기 팝업이 열리면
- **Then**:
  - 팝업 상단에 **인증 상태 뱃지**(VERIFIED/UNVERIFIED)가 표시된다.
  - **차대번호(VIN) 필드**가 표시된다.
    - 통합DB와 연동되어 VERIFIED인 차량: VIN이 읽기 전용으로 표시되고 옆에 **[차량등록증 보기]** 버튼이 표시된다.
    - UNVERIFIED 차량 또는 VIN 미등록 차량: VIN 입력 필드가 활성화되어 운영자가 직접 입력 또는 수정할 수 있다.
    - 통합DB 연동 전 초기 상태: "미등록" 플레이스홀더로 표시.
  - **서비스 정보 영역** → **차량 정보 영역** → **단말기 정보 영역**이 섹션 구분선으로 시각적으로 분리된다.
  - 서비스 정보 영역에 서버 반영 카코드 드롭다운이 표시된다. (기존 Model Code 명칭 변경·이전. Protocol Model Code는 단말기 SN으로 통일되어 단말기 정보 영역에 표시됨)
  - **단말기 정보 영역**에 **단말기 기종**(읽기 전용) 및 **단말기 SN**(읽기 전용) 필드가 표시된다. (변경-Z, 변경-W)
  - 승차정원 필드는 표시되지 않는다. (변경-AA)
  - [저장] 버튼 클릭 시 변경된 내용이 저장된다.

### [기능 B-4-1] 차량 수정 팝업 — VIN 입력 및 저장

- **Given**: 운영자가 UNVERIFIED 또는 VIN 미등록 차량의 수정 팝업을 열고 VIN을 입력한 상태에서
- **When**: [수정] 버튼을 클릭하면
- **Then**:
  - 입력된 VIN 형식을 검증한다 (17자리, 영문 대문자 + 숫자, I/O/Q 제외).
  - 형식 오류 시: "차대번호는 영문 대문자와 숫자 17자리입니다 (I, O, Q 제외)" 에러 메시지 표시.
  - 형식 유효 시: 차량 수정이 저장된다. 인증 상태는 UNVERIFIED 유지.
  - 저장 성공 시: "차량 정보가 수정되었습니다" Toast 메시지 표시.

### [기능 B-4-2] 차량 등록증 보기 (VERIFIED 차량 전용)

- **Given**: 운영자가 VERIFIED 차량의 수정 팝업을 열고 [차량등록증 보기] 버튼을 클릭한 상태에서
- **When**: 버튼을 클릭하면
- **Then**:
  - 차량등록증 이미지가 새 탭 또는 모달로 열린다.
  - 등록증이 복수 업로드된 경우 가장 최신 발부일자 등록증이 기본으로 표시되며, 이전 이력을 확인할 수 있는 탭 또는 목록이 제공된다.

### [기능 B-4-3] UNVERIFIED 차량 — 차량등록증 업로드 (인증 전환)

- **Given**: 운영자가 UNVERIFIED 차량의 수정 팝업을 열고 [차량등록증 업로드] 버튼을 클릭한 상태에서
- **When**: 차량등록증 이미지를 업로드하면
- **Then (Frontend)**:
  - OCR 분석 수행 후 추출된 VIN을 현재 `vehicle_temp`(임시DB) 또는 `vehicle_immutable`(차량DB)의 VIN과 비교한다.
  - **VIN 일치**: "차량등록증이 확인되었습니다. 인증 완료로 전환합니다." 확인 모달 표시 후 전환.
    - 인증 상태 뱃지가 UNVERIFIED(회색) → VERIFIED(녹색)로 변경됨.
    - [차량등록증 업로드] 버튼이 [차량등록증 보기] 버튼으로 전환됨.
  - **VIN 불일치**: "등록증의 차대번호가 현재 등록된 차대번호와 일치하지 않습니다. 등록증을 다시 확인해 주세요." 에러 표시. 업로드 차단.
- **Then (Backend/API)**:
  - `vehicle_registration_docs` INSERT (`is_verified_source = true`).
  - `vehicle_temp`의 경우: 승격(Promotion) 워크플로우 실행 → `vehicle_immutable + vehicle_mutable INSERT`, `vehicle_temp DELETE` (통합DB PRD §6.3). `vehicle_mutable.verification_status = VERIFIED` 설정.
  - 등록증 기반 변경 필드에 대해 `vehicle_change_history` INSERT (`source_doc_url` 포함).
  - HTTP 200 OK 반환. (통합DB PRD v2.4 [기능 8] 준용)

### [기능 B-5] 차량위치 수정 (현행 유지)

- **Given**: 운영자가 상세보기 팝업에서 [차량위치수정] 버튼을 클릭한 상태에서
- **When**: 차량위치 수정 팝업이 열리면
- **Then**: 현행과 동일하게 기존 위치 표시, 변경 위치 입력, 카카오맵 지도 UI가 표시된다.

## 8. 통합DB 구축 프로젝트와의 역할 분리 (Role Separation)

### 8.1 역할 분리 원칙

본 프로젝트와 상위 프로젝트(차량정보 통합DB 구축)의 역할은 다음과 같이 명확히 분리됩니다.

| 영역 | 본 프로젝트 (FMS UI) | 통합DB 구축 프로젝트 (DB/API MVP) |
| :--- | :--- | :--- |
| 차량 등록 모달 UI (Path A/B/C 구조) | ✅ 전체 UI 구현 (드롭존, OCR 상태, API 자동 채움, Path C 직접 입력) | ❌ |
| 차량 수정 팝업 UI | ✅ 필드 추가/재배치 | ❌ |
| 차량관리 목록 UI | ✅ 컬럼/필터 정리 | ❌ |
| 카코드 분리 | ✅ 메뉴 구조 개편 | ❌ |
| 통합 Vehicle API 백엔드 | ❌ | ✅ (MVP: 저장/조회) |
| OCR 서버/소유주 검증 API | ❌ | ✅ |
| vehicle_immutable / vehicle_mutable / vehicle_temp DB 스키마 | ❌ | ✅ |
| 기존 5만 대 데이터 마이그레이션 | ❌ | ✅ |

### 8.2 연계 순서

본 프로젝트의 FMS UI 개선이 통합DB 구축 프로젝트의 API 연동보다 **선행**하여 진행될 수 있습니다. 초기에는 VIN 필드가 수동 입력/미등록 상태로 운영되다가, 통합DB API가 준비되면 자동 연동됩니다.

```
[본 프로젝트] 카코드 관리/차량관리 구조개선 (FMS UI)
  └─ 차량 등록 모달에 VIN 필드 추가 (수동 입력 가능)
  └─ 차량 수정 팝업에 VIN/인증 상태 추가 (수동 입력 가능)
  └─ 카코드 분리
        ↓ (병행 또는 후속)
[상위 프로젝트] 통합DB 구축 (DB/API MVP)
  └─ vehicle_immutable + vehicle_mutable + vehicle_temp 테이블 및 API 구축
  └─ OCR/소유주 검증 API 연동
  └─ FMS ↔ 통합DB 실시간 연동 (VIN 매칭, VERIFIED 전환)
```

## 9. 차선 과제 — 카코드 통합/폐합 기능 (별도 우선순위 논의)

> ℹ️ 아래 내용은 이번 스프린트의 우선 과제가 아닙니다. 개발 복잡도가 높아 별도 논의 후 일정을 결정합니다.

### 8.1 배경

동일 차종/연식에 대해 여러 카코드가 분산 등록되어 있는 경우, 신규 통합 카코드를 만들어 기존 복수 카코드를 폐합하고, 해당 카코드를 사용 중인 모든 차량에 신규 카코드를 일괄 적용해야 하는 니즈가 있습니다.

### 8.2 요구사항 초안

- 카코드 관리에서 복수의 카코드를 선택하여 '통합/폐합' 액션 수행
- 통합할 대상 카코드들을 선택하고, 대체할 신규 카코드를 지정 (기존 카코드 중 선택 또는 신규 생성)
- 통합 대상 카코드들을 사용 중인 모든 차량의 카코드가 신규 카코드로 일괄 변경됨
- 폐합된 카코드는 '폐합' 상태로 변경되어 신규 차량 등록 시 선택 불가

### 8.3 개발 영향도

- 카코드 관리 UI: 카코드 다중 선택 + 통합/폐합 UI 추가
- 서버: 카코드 상태 필드(ACTIVE/DEPRECATED) 추가, 일괄 업데이트 API 구현
- 차량 관리: 카코드 대량 변경 트랜잭션 처리

## 11. imsform 차량 카테고리 DB 연동

### 11.1 연동 목적

현재 FMS 어드민에서 카코드(카코드 관리) 등록 시 제조사·모델명·차량종류·유종·승차인원을 운영자가 직접 자유 입력하는 방식으로 운영됩니다. 이로 인해 동일 모델이 다양한 표기로 등록되는 데이터 불일치 문제가 발생합니다.

이번 개선에서 **imsform 서비스가 차량 다건 등록에 활용하는 차량 카테고리 DB(imsform_차량카테고리.xlsx Sheet2)**를 FMS에 연동하여, 입력 방식을 **사전 정의된 데이터 기반의 선택형(드롭다운)**으로 전환합니다.

### 11.2 연동 데이터 출처

### 카테고리 A. 메뉴 역할 분리 정책

#### BR-01. 카코드 관리 메뉴의 역할 범위

- 카코드 관리 메뉴는 **카코드 데이터의 등록, 수정, 삭제, 일괄등록**만을 담당한다.
- 카코드 관리 메뉴에서는 차량 데이터의 등록, 수정, 삭제를 수행할 수 없다.
- 카코드 관리 메뉴에는 차량 등록 버튼, 차량 일괄등록 버튼을 제공하지 않는다.

#### BR-02. 차량관리 메뉴의 역할 범위

- 차량관리 메뉴는 **차량 데이터의 등록, 수정, 삭제, 일괄등록** 전체를 담당한다.
- 차량 등록의 유일한 진입점은 차량관리 메뉴이다. 카코드 관리 메뉴를 통한 차량 등록 진입은 허용하지 않는다.

#### BR-03. 메뉴 간 독립성

- 차량 등록 시 카코드 선택은 필수가 아닌 선택 사항이다.
- 카코드가 등록되지 않은 상태에서도 차량 등록이 가능해야 한다.
- 카코드가 없는 차량의 서버 반영 카코드 필드는 빈 값(NULL)으로 저장된다.

### 카테고리 B. 카코드 관리 정책

#### BR-04. 카코드 정의

- 카코드란 차량 단말기에 적용하는 펌웨어의 코드명으로 정의한다.
- 카코드는 FMS 시스템에서 차량 단말기 설정을 위한 내부 식별 코드이며, 통합DB 구축 프로젝트의 차량 VIN(차대번호)과는 별개의 개념이다.

#### BR-05. 카코드 용어 통일

- FMS 어드민 UI 레이블(표시명)에서 카코드 관련 용어는 **카코드**로 통일하여 표기한다.

#### BR-07. 카코드 중복 등록 금지

- 동일한 카코드 값을 중복 등록할 수 없다.
- 등록 시 중복 여부를 서버에서 검증하고, 중복 시 에러 메시지를 반환한다.

#### BR-08. 카코드 삭제 시 차량 연결 처리

- 삭제하려는 카코드를 현재 차량에서 사용 중인 경우, 삭제 전 운영자에게 사용 중인 차량 수를 안내하고 확인을 받아야 한다.
- 운영자가 삭제를 확인한 경우, 해당 카코드를 사용 중인 모든 차량의 서버 반영 카코드 필드를 NULL로 초기화한다.
- 삭제된 카코드는 복구할 수 없다.

### 카테고리 C. 차량 관리 정책

#### BR-09. 차량 등록 진입점

- 차량 등록은 반드시 **차량관리 메뉴**에서 진행한다. 카코드 관리 메뉴에서는 차량 등록이 불가하다.

### 카테고리 F. imsform 차량 카테고리 DB 연동 정책

> ℹ️ **적용 범위 요약**:
> - 카코드 등록/수정: 모든 경로에서 imsform DB 캐스케이드 적용
> - 차량 등록 모달: **Path C(직접 입력) 전용**으로 적용. Path A(OCR 자동 채움), Path B(API 자동 채움)에서는 적용하지 않음
> - 차량 수정 팝업 제조사/모델 필드: 선택형 전환 여부 TBD (개발팀 협의 필요)

#### BR-17. 차량 카테고리 데이터 출처 및 관리 원칙

- FMS 어드민의 카코드 등록/수정 화면에서 사용하는 브랜드·모델·차종·유종 데이터는 **imsform 차량 카테고리 DB**를 단일 출처(SSOT)로 한다.
- 데이터는 `vehicle_brand`, `vehicle_model`, `vehicle_meta` 테이블로 관리하며, imsform DB 업데이트 시 FMS DB와 동기화한다.
- 운영자가 임의로 브랜드/모델을 신규 생성하는 기능은 제공하지 않는다. 신규 브랜드/모델 추가는 imsform 차량 카테고리 DB 업데이트를 통해서만 반영된다.

#### BR-18. 제조사·모델명 선택 계층 구조

- 카코드 등록/수정 화면에서 제조사 선택은 **국산차/수입차 구분 선택 → 브랜드 선택 → 모델 선택** 3단계 계층 구조로 동작한다.
- 국산차와 수입차의 브랜드 목록은 분리하여 제공한다.
  - 국산차 브랜드: 현대, 기아, 제네시스, 르노삼성, 쉐보레, 쌍용, 예스알브이, 스타모빌, 다온티앤티, 기타_국산
  - 수입차 브랜드: 벤츠, BMW, 아우디 외 55개 브랜드
- 브랜드를 선택하지 않은 상태에서 모델 드롭다운은 비활성화(disabled)된다.
- 브랜드를 변경하면 기존에 선택된 모델 값이 초기화된다.
- **적용 범위 (260715 확대)**: 본 계층 구조는 카코드 등록/수정 화면뿐 아니라, **차량 등록 모달(§4.2.2)의 Path A/B/C 전체**에 적용된다. Path A(OCR)·Path B(소유주 검증 API)는 추출된 브랜드·모델 값으로 드롭다운을 사전 선택(pre-select)하고, 운영자가 재선택하여 변경할 수 있다. Path C는 처음부터 직접 선택한다. (기존에는 Path C 전용이었음)

#### BR-19. 차종에 따른 승차인원 범위 연동

- 차량종류(차종)를 선택하면 승차인원 드롭다운에 해당 차종의 가능한 인원 범위만 표시된다.
  - sedan: 1 ~ 5인
  - SUV: 3 ~ 15인
  - RV: 3 ~ 15인
  - etc: 1 ~ 15인
- 차량종류를 선택하지 않은 상태에서 승차인원 드롭다운은 비활성화(disabled)된다.
- 차량종류를 변경하면 기존에 선택된 승차인원 값이 초기화된다.

#### BR-20. 레거시 데이터 호환 처리

- imsform DB 연동 전 자유 입력으로 등록된 기존 카코드의 제조사·모델명 값은 수정 화면에서 기존 텍스트를 그대로 표시한다.
- 기존 값이 imsform DB에 존재하는 경우: 해당 항목을 드롭다운에서 자동 선택(pre-select) 상태로 표시한다.
- 기존 값이 imsform DB에 존재하지 않는 경우: 드롭다운 최상단에 `"(기존값: [원본텍스트])"` 형태로 표시하며, 운영자가 DB 기반 값으로 재선택하거나 기존 값을 유지할 수 있다.
- 레거시 값이 유지된 카코드는 목록 테이블에서 별도 표기(아이콘 등)를 하지 않는다. (운영 혼란 방지)

### 카테고리 G. 카코드 매칭 및 VIN 단독 조회 정책

#### BR-21. 서버 반영 카코드 선택 시 차량 정보 자동 채움

- 차량 등록 모달의 서버 반영 카코드 드롭다운에서 카코드를 선택하면, 해당 카코드에 저장된 차량 제원 정보(유종·배기량·길이 등)를 차량 정보 필드에 자동으로 채운다.
- **드롭다운 목록 필터 (변경-AA)**: 차량 정보에 입력된 제조사·모델명·연식이 동일한 카코드만 표시한다. 각 항목에는 카코드명 + 연식·하위모델명·유종·배기량·길이를 함께 표시한다.
- 자동 채움 대상 필드: 유종, 배기량, 길이. (변경-AA: 승차정원 제거)
- Path A(OCR 자동 채움) 또는 Path B(API 자동 채움) 상태에서 이미 값이 자동 입력된 필드에 대해서는 카코드 매칭으로 덮어쓰지 않는다. 대신 "카코드 정보와 다를 수 있습니다. 직접 확인해 주세요." toast 메시지를 표시한다.
- Path C(직접 입력) 상태에서는 모든 대상 필드를 카코드 매칭 값으로 채운다. 운영자가 이후 수동 수정할 수 있다.
- Path C에서 제조사·모델명(브랜드/모델 드롭다운)도 카코드와 일치하는 값이 있으면 pre-select한다.

#### BR-22. VIN 단독 조회 정책 (Path B 서브모드 B)

- Path B의 서브모드 B(차대번호 단독 조회)는 소유주 검증 없이 VIN만으로 차량 정보를 조회하는 방식이다.
- 입력 형식: 영문 대문자 + 숫자 17자리 (I, O, Q 제외). 형식 불일치 시 인라인 에러 표시 후 조회 중단.
- 조회 성공 시 반환 데이터: 차량번호, 연식, 제조사, 유종, 배기량. 파란 배경으로 자동 채움.
- VIN 필드도 입력값으로 자동 채움.
- 소유주 검증이 수행되지 않으므로 인증 상태는 항상 UNVERIFIED로 유지된다. 이를 운영자에게 명확히 안내한다.
- 차명·최초등록일은 VIN 조회로 반환되지 않으므로 수동 입력 필수(빨간 테두리 표시).

### 카테고리 H. 통합DB 연동 차량 등록 정책

#### BR-23. Path A VIN 기반 통합DB 중복 체크 정책

Path A(차량등록증 업로드)에서 OCR 완료 후 VIN 17자리가 확정되면 통합DB에 VIN 기준 중복 조회를 자동 수행한다. **Path B/C는 통합DB를 조회하지 않고 항상 임시DB(`vehicle_temp`)에 등록한다.**

| 케이스 | 판단 기준 | 프론트엔드 처리 | 백엔드 처리 |
| :--- | :--- | :--- | :--- |
| Case A (신규) | VIN이 통합DB에 없음 | 안내 없이 정상 진행 | `vehicle_immutable + vehicle_mutable INSERT` |
| Case B (동일 등록증 중복) | 동일 VIN + 동일 발부일자 등록증 존재 | "이미 등록된 차량 등록증입니다" 안내 + 등록 차단 | 등록 요청 거부 |
| Case C-1 (동일 VIN, 다른 등록증 — 업로드본이 최신) | 동일 VIN, 발부일자 다름, 업로드본이 기존 최신 등록증과 같거나 더 최신 | "이전 등록증 이력이 존재합니다" 안내만 표시, 등록 진행 가능 | 신규 `vehicle_registration_docs INSERT` + 이력 관리, 업로드본 기준으로 데이터 갱신 |
| Case C-2 (동일 VIN, 다른 등록증 — 업로드본이 구버전, 260715 신규) | 동일 VIN, 발부일자 다름, 업로드본이 기존 최신 등록증보다 이전 | "업로드된 등록증보다 더 최신화된 등록증이 있습니다. 차량등록증을 다시 확인하세요." 안내 팝업 표시. 자동 채움 값을 기존 최신 등록증 데이터로 대체. 등록 차단 아님 | 업로드본을 이력으로 INSERT하되, 폼 응답 데이터는 기존 최신 등록증 기준으로 반환 (BR-35 참조) |

- FMS 서비스 연결 버튼은 제공하지 않는다. (운영자 혼란 방지, 2026-06-04 사용자 확인 결정)

#### BR-34. FMS 자체 차대번호·차량번호 중복 등록 방지 정책 (260715 신규)

- [등록하기] 버튼 클릭 시, Path A/B/C 공통으로 **FMS 자체 차량관리 데이터를 대상**으로 입력된 차대번호·차량번호의 중복 여부를 검사한다. 이 검사는 통합DB VIN 중복 체크(BR-23)보다 **먼저** 수행된다.
- 동일한 차대번호 **또는** 동일한 차량번호를 가진 **운영 중(차량상태 ≠ 매각) 차량**이 이미 존재하면 등록을 차단하고, "동일한 차대번호(차량번호)가 존재합니다. 기존 차량을 매각 처리한 후 다시 등록하세요." 안내 팝업을 표시한다.
- 매각 처리된(차량상태 = 매각) 차량과 동일한 차대번호·차량번호는 중복으로 간주하지 않으며, 신규 등록을 허용한다. (BR-29 매각 처리 정책과 일관)
- 본 정책은 통합DB가 아닌 **FMS 자체 DB(서비스 DB) 기준**으로 판단하는 별도 검증이며, BR-23(통합DB 기준, Path A 전용)과는 독립적으로 동작한다.
- 중복 체크 API 상세 스펙은 FMS 서버팀과 협의가 필요하다 (TBD-11).

#### BR-35. Path A 최신 등록증 자동 비교 정책 (260715 신규)

- Path A(차량등록증 업로드)에서 OCR 완료 후 VIN이 확정되면, BR-23 Case C(동일 VIN·다른 발부일자) 상황에서 업로드된 등록증과 **차량 DB(통합DB)에 존재하는 기존 최신 등록증의 발부일자**를 비교한다.
- 업로드된 등록증이 기존 최신 등록증보다 **구버전(발부일자가 더 이전)** 인 경우:
  - 자동 채움 필드 값을 업로드된 등록증(OCR)의 값이 아닌 **기존 최신 등록증 데이터**로 대체하여 표시한다.
  - "업로드된 등록증보다 더 최신화된 등록증이 있습니다. 차량등록증을 다시 확인하세요." 안내 팝업을 표시한다.
  - 안내는 정보 제공 목적이며 등록 자체를 차단하지 않는다. 운영자가 확인 후 정상적으로 [등록하기]를 진행할 수 있다.
- 업로드된 등록증이 기존 최신 등록증과 같거나 더 최신인 경우 본 정책은 적용되지 않으며, 기존 BR-23 Case C-1 처리를 따른다.
- 발부일자 비교 로직 및 API 상세 스펙은 통합DB 구축 프로젝트와 협의가 필요하다 (TBD-12). 기존 `vehicle_registration_docs` 이력 조회 API 확장으로 구현 가능할 것으로 예상되나 확정 전이다.

#### BR-25. VIN·연식 읽기전용 근거 정책

- **차대번호(VIN)**:
  - 차량의 법적 고유 식별자(ISO 3779 표준). 차량 제조 시 부여되며 변경 불가.
  - **Case 2(등록증 있음)**: 차량등록증 기반으로 확정된 값. 임의 변경 시 통합DB 정합성이 깨지므로 읽기 전용. SYS_ADMIN 권한으로만 변경 가능.
  - **Case 1(등록증 없음)**: 미검증 상태이므로 운영팀이 수동 입력/수정 가능.

- **연식(제조년도)**:
  - 차량등록증 법정 기재 항목.
  - **Case 2(등록증 있음)**: 등록증 기반으로 확정된 값이므로 읽기 전용. 오기재 수정이 필요한 경우 SYS_ADMIN 권한으로만 변경 가능.
  - **Case 1(등록증 없음)**: 등록증 미제출 상태이므로 운영팀이 수동 수정 가능.

- **연식 데이터 출처 정책** *(v2.1 신규)*:
  - 연식(제조년도)은 반드시 **차대번호(VIN) 기반**으로 산출한다. VIN의 10번째 자리(Position 10)는 ISO 3779 표준에 따라 제조연도(Model Year)를 나타내며, 이를 연식 데이터의 기준으로 삼는다.
  - **차량 등록증의 등록일(최초등록일)을 기준으로 연식을 산출하지 않는다.** 최초등록일은 해당 차량이 국내에 최초로 등록된 날짜이며, 실제 제조연도(Model Year)와 다를 수 있다.
  - Path A(OCR) 시: OCR이 등록증에서 읽은 연식 값이 VIN 기반 산출 연식과 불일치하는 경우, **VIN 기반 값을 우선**한다. 불일치 발생 시 주황색 배경 + ⚠ 경고 아이콘으로 운영자에게 확인을 요청한다.
  - Path B(소유주 검증 조회) 시: API 응답의 연식 데이터도 VIN 기반임을 전제하며, 별도 불일치 경고 적용.
  - Path C(직접 입력) 시: 운영자가 VIN을 기준으로 연식을 직접 입력한다.

#### BR-26. 자동 채움 필드 수정 가능 정책

- OCR 또는 소유주 검증 API로 자동 채워진 모든 필드는 **[등록하기] 버튼 클릭 전까지** 운영자가 직접 수정 가능하다.
- 자동 채움 후 수정된 필드는 파란 배경을 유지한다(출처 표시 목적).
- 등록 완료 후에는 각 필드의 변경 불가/가능 여부에 따라 수정이 제한된다.
- VIN 필드는 등록 전에는 수정 가능하나, 등록 완료 후 VERIFIED 상태가 되면 읽기 전용으로 전환된다. (BR-25)

#### BR-24. 차량등록증 사전 검증 정책 (Path A)

- Path A(차량등록증 업로드) 방식으로 파일을 업로드하면, OCR 전 단계에서 파일이 차량등록증인지 사전 검증을 수행한다.
- 사전 검증은 통합 Vehicle API (`POST /api/v1/ocr/validate`)를 통해 수행하며, 파일 업로드 즉시 비동기로 호출한다.
- 사전 검증 순서: 파일 타입/크기 검증 → 사전 검증 API 호출(차량등록증 여부 확인) → OCR 분석 요청.
- 사전 검증 실패 시 OCR 처리를 진행하지 않고 운영자에게 오류 안내를 표시한다: "업로드하신 파일을 차량등록증으로 인식할 수 없습니다. 올바른 차량등록증 이미지를 다시 업로드해 주세요."
- OCR 처리 방식: 비동기 Webhook 방식. API 서버가 OCR 서버에 요청 후 Webhook으로 결과를 수신하며, 처리 중에는 로딩 인디케이터를 표시한다.

### 카테고리 I. 운영팀 요청 반영 정책 (v1.0 신규)

#### BR-27. 리버스 자동 감지 정책

- 카코드의 리버스(O/X) 여부는 **서버에 해당 카코드의 fbp 파일 존재 여부에 따라 자동으로 결정**한다.
- 운영자가 카코드 등록/수정 화면에서 리버스를 수동 설정하는 기능은 제공하지 않는다.
- fbp 파일 존재 시 `O` (녹색 뱃지), 미존재 시 `X` (회색 뱃지)로 시스템이 자동 표시한다.
- 카코드 관리 테이블의 리버스 컬럼은 읽기 전용으로 표시한다.
- fbp 파일 존재 여부를 반환하는 API 또는 DB 필드 설계는 개발팀 협의 필요 (TBD-01).

#### BR-28. 연식 입력 정책 (260609 확정)

- 카코드 관리 카코드 등록/수정 화면의 연식 입력은 **YYYY 숫자 직접입력** 방식을 사용한다.
- 260608에서 검토된 알파벳:연도 드롭다운 방식은 260609 운영팀 최종 확정으로 취소되었다.
- 연식 앞 알파벳 표시(예: X: 2024)는 UI에서 완전 삭제한다.
- TBD-02(연식 코드 저장 방식)는 260609 결정으로 숫자 YYYY 저장으로 해소된다.

### 카테고리 J. 260609 운영팀 추가 요청 정책

#### BR-29. 매각 처리 정책

- 차량 수정(상세보기) 팝업 하단에 **[매각 처리]** 버튼을 제공한다.
- [매각 처리] 클릭 시 컨펌창을 표시한다:
  - **[단말기 연결 유지]**: 연결된 단말기를 유지한 상태로 해당 차량 ID를 매각 상태로 전환.
  - **[단말기 연결 해제]**: 연결된 단말기를 해제하고 해당 차량 ID를 매각 상태로 전환.
  - **[N (취소)]**: 컨펌창 닫기, 매각 처리 미수행.
- 매각 상태로 전환된 차대번호는 신규 차량 등록이 가능하다.

#### BR-30. 서비스정보 변경 시 컨펌창 정책

- 차량 수정 팝업에서 서비스 정보(업체 또는 지점)를 변경 후 [저장] 버튼을 클릭하면 컨펌창을 표시한다.
- 컨펌 내용: "해당 차대번호의 이전 ID를 매각 처리하고 새로운 ID를 생성합니다. 연결된 단말기는 유지됩니다. 동의하십니까?"
  - **[확인]**: 이전 ID 매각 처리 + 새 ID 생성 + 단말기 연결 유지.
  - **[취소]**: 컨펌창 닫기, 저장 미수행.
- 서비스 정보(업체/지점) 외 다른 필드만 변경한 경우에는 컨펌창을 표시하지 않는다.

#### BR-31. 차량 삭제 정책

- 삭제 버튼은 차량 수정(상세보기) **팝업 내부**에 위치한다 (목록 테이블 인라인 삭제 버튼 제거).
- 삭제는 **서비스 DB에서만** 수행된다. 차량 DB(통합DB)에서는 삭제되지 않는다.
- 단말기가 연결된 차량은 삭제 불가 (버튼 비활성화).
- 단말기가 연결되지 않은 차량만 삭제 가능.

### 카테고리 K. 등록 예정 목록(Staging) 배치 등록 정책 (v1.2 신규 / v1.4 재설계 / v1.5 모달 닫기 정책 추가)

#### BR-32. 차량 일괄등록 — 등록 예정 목록 정책 (v1.5 갱신)

- **등록 예정 목록은 차량 등록 팝업 좌측 패널(차량 정보 가져오기 섹션) 하단에 표시된다.** 별도 모달은 사용하지 않는다.
- **모달 외부(backdrop) 클릭으로는 닫히지 않는다.** 반드시 [×] 닫기 또는 [취소] 버튼을 사용해야 한다.
- **[×] 닫기 / [취소] 클릭 시**: 등록 예정 목록이 0건이면 즉시 닫힌다. 1건 이상이면 "등록 예정 N건이 있습니다. 취소 시 등록 예정 목록이 초기화됩니다. 계속하시겠습니까?" 확인 다이얼로그를 표시한다. 확인 시 목록을 초기화하고 닫는다. 취소 시 모달을 유지한다.
- **[차량 일괄등록] 버튼은 제거된다** (v1.5). [차량 등록] 버튼이 단건·다건 모두 담당한다.
- 목록은 **브라우저 세션 단위**로 유지된다. 브라우저 탭 종료 또는 새로고침 시 초기화된다.
- 등록 예정 목록 최대 건수는 **10건**이다. 초과 시 [목록에 추가] 버튼 비활성화 및 안내 토스트 표시.
- 목록에 항목이 1건 이상이면 목록 영역이 표시되고, 0건이면 숨겨진다.
- 경로별 목록 추가 방법:
  - **Path A (등록증 OCR)**: OCR 완료 시 **자동으로** 목록에 추가된다. 드롭존이 리셋되어 다음 등록증 업로드 대기 상태가 된다.
  - **Path B (소유주 검증 조회)**: 조회 성공 후 표시되는 **[목록에 추가]** 버튼 클릭 시 추가된다.
  - **Path C (직접입력)**: **[목록에 추가]** 버튼이 항상 표시되며 클릭 시 추가된다.
- 목록 항목의 인증 상태(VERIFIED/UNVERIFIED)는 진입 경로에 따라 자동 설정된다.
  - Path A(등록증 OCR): VERIFIED
  - Path B(소유주 검증 조회), Path C(직접입력): UNVERIFIED
- 목록에서 **[삭제]** 클릭 시 해당 항목이 제거된다.
- **[등록하기 (N건)]** 클릭 시 목록 전체를 `POST /api/v1/vehicles/bulk` API로 비동기 일괄 등록한다.
- 등록 결과는 `{ success: N, skipped: N, failed: N }` 형태로 토스트 표시 후 팝업을 닫는다.
- 목록이 0건일 때 [등록하기]는 현재 경로 단건 등록(`POST /api/v1/vehicles`)으로 동작한다.
